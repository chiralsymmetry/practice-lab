# Practical Cryptography — Dynamic Practice Specification

Status: implementation specification

Audience: exercise-generator, byte/cipher oracle, controlled-protocol simulator, answer-checker, and UI implementers

Normative language: **must**, **must not**, **should**, and **may** have their usual requirements meanings.

## 1. Topic overview

### Topic name

Practical Cryptography

### Topic goal

Develop accurate operational reasoning about cryptographic transformations and security properties. The learner should become able to:

- encode and decode small messages with Caesar, affine, monoalphabetic, and Vigenère ciphers;
- infer missing keys or mappings from controlled known-plaintext evidence;
- compute XOR over bits, bytes, and short byte strings in either direction;
- explain exactly what makes a one-time pad a one-time pad;
- recognize the information exposed by pad, keystream, or nonce reuse;
- distinguish encoding, encryption, hashing, authentication, and signing;
- assign the roles of keys, nonces, salts, tags, associated data, and randomness;
- reason about authenticated-encryption records and reject unsafe constructions;
- choose hashes, MACs, password KDFs, signatures, and encryption for the guarantees they actually provide;
- trace small hybrid-encryption, key-exchange, signature, certificate, and replay-protection workflows;
- recognize that toy and historical ciphers teach mechanics but are not secure systems.

### Position within Practice Lab

This app owns cryptographic transformations, security goals, primitive selection, and protocol-use reasoning.

- **Programmer Low-Level Numeracy** owns general binary/hex conversion and bitwise arithmetic; this app reapplies those skills to bytes and keystreams.
- **Number Theory and Modular Arithmetic** owns modular inverses, exponentiation, and the arithmetic inside toy RSA/affine examples; this app owns cipher mappings and security interpretation.
- **Probability and Statistics** owns general collision and birthday-problem calculation; this app may use supplied collision probabilities to make nonce/salt decisions.
- **Admin Practice** owns command syntax and certificate-file administration; this app owns what cryptographic artifacts mean.
- **Computer Science** owns generic data structures and algorithms; this app owns the threat model and security guarantees.

### Audience and prerequisites

The learner should know:

- arithmetic modulo 26 for the classical-cipher categories;
- binary and hexadecimal byte notation for XOR categories;
- basic probability language such as “uniform,” “independent,” and “collision” for later categories;
- the idea that communicating parties and attackers may see different information.

The app must provide brief refreshers and representation scaffolds. It must not require abstract algebra, cryptographic proofs, or implementation experience.

### Scope

The initial topic includes:

- confidentiality, integrity, authenticity, freshness, and public verifiability as distinct requested properties;
- text-to-symbol and text-to-byte encodings needed by the exercises;
- Caesar/ROT, affine, arbitrary monoalphabetic substitution, and Vigenère/repeating-key substitution;
- controlled classical cryptanalysis using known plaintext, pattern constraints, frequency evidence, and tiny exhaustive keyspaces;
- XOR truth tables, bytes, byte strings, missing operands, repeating keys, and bit-flip propagation;
- one-time-pad requirements, encryption/decryption, reuse leakage, known-plaintext consequences, malleability, and key accounting;
- stream-cipher nonce/counter structure at a conceptual byte-stream level;
- block-cipher modes only where they teach visible security consequences: ECB pattern leakage, padding length, and why unauthenticated encryption is insufficient;
- authenticated encryption with associated data (AEAD), nonce uniqueness, tags, record inputs, and fail-closed verification;
- hashes, MACs, password KDFs, salts, digest/tag representations, and integrity-versus-authenticity distinctions;
- public/private key roles, signatures, hybrid encryption, ephemeral key exchange, certificates, trust paths, and replay protection;
- generated decision and timeline questions about key/nonce lifecycle and safe API use.

### Exclusions

Do not include in the initial app:

- real-world ciphertext cracking, password recovery, credential attacks, malware, exploit development, traffic interception, or targets not generated by the app;
- production key generation, key custody, certificate issuance, or deployment instructions;
- hand-written implementations of AES, ChaCha20, Poly1305, SHA-2/3, elliptic curves, RSA padding, or arbitrary cryptographic protocols;
- raw textbook RSA as a recommended encryption/signature construction;
- obsolete algorithms presented without an explicit insecure/deprecated label;
- detailed differential/linear cryptanalysis, side-channel exploitation, fault attacks, lattice attacks, or cryptographic proofs;
- steganography, cryptocurrency, blockchain consensus, zero-knowledge systems, post-quantum schemes, or homomorphic encryption in v1;
- memorizing numeric algorithm parameters that an established API should select;
- open-ended “design a secure protocol” grading;
- claims that encryption alone authenticates, hashes prove authorship, or signatures inherently provide confidentiality;
- legal or organizational claims of “non-repudiation” inferred from a signature without identity, custody, policy, and dispute-resolution context;
- any exercise that asks the learner to paste secrets, real tokens, private keys, password hashes, or personal messages.

### Safety and instructional boundary

Every Caesar, affine, substitution, Vigenère, repeating-key XOR, and tiny public-key arithmetic prompt must carry the persistent label:

> Educational toy — insecure for real data.

Historical cryptanalysis operates only on app-generated text from bounded fixture vocabularies. The app must never accept external ciphertext as a cracking target.

Modern primitives are taught as established black boxes with defined inputs, outputs, and guarantees. Worked solutions say “use a vetted cryptographic library/protocol” rather than encouraging implementation from scratch.

### Normative symbol and byte conventions

- A byte is an unsigned octet `0..255`.
- Hex bytes use two uppercase digits: `00` through `FF`.
- Binary bytes use exactly eight bits, most-significant bit first.
- Multi-byte strings display bytes left to right in transmission order, separated by one space.
- `⊕` means bitwise XOR on equally sized bit/byte strings.
- XOR has the identities `x⊕0=x`, `x⊕x=0`, and `(x⊕k)⊕k=x`.
- Unless UTF-8 is the skill being tested, text-byte exercises use printable ASCII and show the encoding table or relevant byte values.
- Base64 is an encoding, not encryption. Base64 mechanics may appear only as representation support, not as a major category.
- A cryptographic hash is modeled as a deterministic fixed-length digest; a MAC additionally requires a secret key.
- A tag comparison is semantic pass/fail. The UI never implies that a partially matching tag is “almost valid.”

### Classical-cipher conventions

- The default alphabet is uppercase English `A..Z`, encoded `A=0,...,Z=25`.
- Caesar encryption is `E_k(x)=(x+k) mod26`; decryption is `D_k(y)=(y−k) mod26`.
- Caesar keys are canonical residues `0..25`; exercises normally reject the identity key `k=0` unless identity behavior is the point.
- Affine encryption is `E_{a,b}(x)=(ax+b) mod26`.
- An affine multiplier is valid exactly when `gcd(a,26)=1`; decryption is `a⁻¹(y−b) mod26`.
- A monoalphabetic substitution key is a permutation. A displayed mapping `plain → cipher` is used in that direction for encryption and inverted for decryption.
- Vigenère uses `C_i=(P_i+K_i) mod26`, with `A=0`. The key repeats over letters only; spaces and punctuation are preserved and do not advance the key unless a prompt explicitly declares another convention.
- Case, spaces, and punctuation are preserved for display but are not cryptographic alphabet symbols.

### One-time-pad and stream conventions

- A one-time pad key must be uniformly random, independent of the plaintext, at least as long as the plaintext, kept secret, and never reused.
- A human-chosen word, repeating short key, pseudorandom stream with a reused nonce, or reused random pad is not a one-time pad.
- OTP and stream examples use `C=P⊕K`.
- Reusing the same pad/keystream gives `C₁⊕C₂=P₁⊕P₂`; it does not directly reveal either plaintext without more information.
- Flipping ciphertext mask `Δ` before unauthenticated XOR decryption flips the same plaintext bits: `(C⊕Δ)⊕K=P⊕Δ`.
- A modern stream/AEAD nonce generally need not be secret but must satisfy the algorithm’s uniqueness rule under a key. The exact rule is stated in the prompt.

### Modern-cryptography conventions

- “Encryption” means a standard randomized/nonce-based scheme, never raw block-cipher application.
- Authenticated encryption returns ciphertext plus a tag and verifies before releasing plaintext.
- Associated data (AAD) is authenticated but not encrypted.
- Hashes alone provide change detection only when the expected digest is trusted through another channel.
- A MAC provides integrity and source authentication among parties that share its key; it does not provide public verifiability.
- A digital signature uses a private signing key and a public verification key; it does not encrypt the message.
- Password storage uses a per-record salt and a password KDF with a cost parameter; passwords are not “encrypted for comparison.”
- A nonce, salt, IV, key, and tag are distinct roles even when each is represented as bytes.
- Public-key encryption in practice uses a hybrid design: public-key/KEM operation protects a random session key, and AEAD protects the data.

### Global answer conventions

- Surrounding whitespace is ignored.
- Hex is case-insensitive on input; feedback renders uppercase two-digit bytes.
- Optional `0x` is accepted for one byte but not inside a space-separated byte sequence unless the prompt demonstrates it.
- Binary may use an optional `0b` prefix for a single byte; leading zeros remain required when width is tested.
- Classical-cipher letter answers are case-insensitive; feedback renders uppercase and preserves prompt punctuation.
- Byte-string answers must contain the exact byte count. Spaces, hyphens, or colons are accepted as separators if unambiguous.
- A key shift may be entered as any congruent integer unless canonical form is explicitly requested.
- Ordered protocol steps are order-sensitive. Sets of properties or compromised records are order-insensitive.
- Semantic answers such as “reject,” “cannot determine,” “not authenticated,” and “unsafe due to nonce reuse” are distinct.
- Multiple mathematically equivalent XOR groupings are accepted in structured-expression questions after normalization.
- Natural-language security explanations are not free-graded; reasons are chosen from controlled claims or assembled from structured fields.

### Difficulty philosophy

Difficulty should rise through:

- changing direction from encrypt to decrypt or recovering a missing operand;
- moving between letters, indices, bits, bytes, and hex;
- weakening or removing alignment scaffolds;
- tracking a key across punctuation or multiple records;
- distinguishing what an attacker can derive from what remains unknown;
- composing confidentiality, integrity, freshness, and identity requirements;
- tracing state across nonce counters, records, and key rotations;
- diagnosing plausible misuse rather than recalling a label;
- selecting a primitive when several provide overlapping but nonidentical properties.

Difficulty must not rise through:

- long ciphertexts, tedious arithmetic, or huge lookup tables;
- obscure historical-cipher trivia;
- memorizing entire standard test vectors;
- ambiguous prose or unstated text encodings;
- asking learners to compute production ciphers by hand;
- trick questions about library-specific defaults not supplied in the prompt;
- arbitrary time pressure;
- real-world attack targets.

### Topic-wide level model

| Level | Typical demand |
|---|---|
| 1 | One direct mapping, one byte/XOR, or explicit property distinction |
| 2 | Short strings, inverse operations, supplied mapping/key, one protocol condition |
| 3 | Missing key/mapping, mixed representations, reuse analysis, two-step workflow |
| 4 | Controlled cryptanalysis, multiple records, AEAD state/timeline, property composition |
| 5 | Diagnose a realistic bounded misuse scenario and choose a safe correction |

### Generator and oracle model

Every instance stores:

`categoryId`, `subcategoryId`, `familyId`, `level`, `securityLabel`, `alphabet`, `symbolEncoding`, `textEncoding`, `plainBytes`, `keyBytes`, `cipherBytes`, `mapping`, `nonceState`, `recordSet`, `requiredProperties`, `attackerKnowledge`, `canonicalAnswer`, `acceptedAnswerClass`, `difficultyDimensions`, `misconceptionsTargeted`, `distractorProvenance`, `workedSolution`, `structuralSignature`, `fixtureVersion`, and `oracleVersion`.

## 2. Category: Cryptographic language and representations

### Category purpose

Build the vocabulary and byte representation needed to reason about later transformations without conflating security goals.

### Learn

Encoding changes representation; encryption uses a key for confidentiality; hashing maps data to a fixed-length digest; a MAC authenticates data with a shared secret; a signature is verified with a public key. Bytes can be shown as binary, hex, ASCII, or Base64 without changing their underlying values.

### Prerequisites

Basic binary/hex recognition. Provide an inline conversion table at early levels.

### Category boundaries

This category classifies operations and converts small representations. It does not teach general number-base arithmetic or ask learners to calculate production hash/cipher outputs.

### Common misconceptions

- Calling Base64 encryption because text becomes unreadable.
- Assuming a hash can be decrypted.
- Treating a checksum/hash as proof of sender identity.
- Treating a public key as secret.
- Confusing secrecy of a value with uniqueness of a value.

### Family `crypto_operation_classify`

**Task.** Classify a shown transformation as encoding, encryption, hashing, MAC, or signature.

**Response and template.** Single choice: `The operation takes {inputs} and produces {output_description}. What kind of operation is it?`

**Derivation.** Match required inputs and verification/reversal behavior to the normative definitions.

**Difficulty.** L1 Base64 versus encryption; L2 hash versus MAC; L3 MAC versus signature.

**Examples.**

1. Bytes become Base64 text with no key and can be reversed → encoding. L1; targets unreadable=encrypted.
2. Message plus secret key produces a tag checked by another key-holder → MAC. L2.
3. A private key produces a value anyone with the public key can verify → signature. L3.

**Distractors and validation.** Choices correspond to role confusions. Rule table must yield exactly one answer.

### Family `security_property_select`

**Task.** Select which guarantees a scenario requires or supplies.

**Response and template.** Multiple choice: `For {scenario}, which of confidentiality, integrity, authenticity, and freshness are required/provided?`

**Derivation.** Evaluate each property independently from the stated attacker and workflow.

**Difficulty.** L1 one property; L2 two; L3 distinguish integrity/authenticity/freshness.

**Examples.**

1. Hide a diary from a reader → confidentiality. L1.
2. Compare a download against an expected digest obtained through a separately authenticated channel → integrity relative to that digest; origin depends on the channel’s identity binding. L2.
3. Accept a bank instruction only from Alice and only once → authenticity, integrity, and freshness/replay protection. L3.

**Distractors and validation.** “Encryption gives everything” or integrity=authenticity. Scenario property bitset oracle.

### Family `role_material_match`

**Task.** Match key, nonce, salt, tag, digest, and associated data to their roles.

**Response and template.** Matching: `Match each value in {record_diagram} to its cryptographic role.`

**Derivation.** Use generation/storage/visibility/uniqueness and verification semantics.

**Difficulty.** L1 key versus nonce; L2 salt/tag; L3 AAD/digest/multiple records.

**Examples.**

1. Secret value shared by encryptor/decryptor → key. L1.
2. Public per-password random value stored beside the KDF result → salt. L2.
3. Unencrypted record header covered by AEAD verification → associated data. L3.

**Distractors and validation.** Secret nonce/public key/tag as checksum. Typed role assignments are unique.

### Family `byte_representation_convert`

**Task.** Convert one byte among binary, hexadecimal, and decimal.

**Response and template.** Fixed-width string/integer: `Write {value} as {target_representation}.`

**Derivation.** Convert the same 8-bit value; pad binary to 8 bits and hex to 2 digits.

**Difficulty.** L1 nibble-aligned; L2 arbitrary byte; L3 recover from mixed labeled fields.

**Examples.**

1. `01000001₂` → `41₁₆`. L1.
2. `B6₁₆` → `10110110₂`. L2.
3. decimal 255 → hex `FF` and binary `11111111`. L3.

**Distractors and validation.** Decimal reading of hex or lost leading zeros. Integer equivalence plus width.

### Family `ascii_bytes_encode`

**Task.** Convert a short displayed ASCII string to/from hex bytes using supplied character values.

**Response and template.** Text/byte string: `Using ASCII, encode/decode {value}.`

**Derivation.** Map each character independently; preserve byte order.

**Difficulty.** L1 one character; L2 short word; L3 spaces/punctuation or missing byte.

**Examples.**

1. `A` → `41`. L1.
2. `CAT` → `43 41 54`. L2.
3. `48 69 21` → `Hi!`. L3.

**Distractors and validation.** Alphabet indices or reversed byte order. Built-in versioned ASCII table.

### Family `encoding_round_trip`

**Task.** Determine which transformations preserve bytes and can be reversed without a secret.

**Response and template.** Yes/no or ordered sequence: `Can {representation} recover the original bytes without a key?`

**Derivation.** Decode the specified hex/Base64/text representation; distinguish invalid Unicode/text decodes.

**Difficulty.** L1 hex; L2 Base64/padding; L3 text encoding explicitly differs.

**Examples.**

1. Hex `00 FF` preserves both bytes → yes. L1.
2. Base64 text plus its alphabet/padding rules is reversible without a secret → yes, and therefore not encryption. L2.
3. Interpreting arbitrary bytes `FF` as ASCII is invalid; showing `FF` in hex remains lossless. L3.

**Distractors and validation.** “Unreadable means irreversible.” Decode/re-encode equality.

### Family `primitive_capability_matrix`

**Task.** Mark which operations are keyed, reversible, fixed-length, or publicly verifiable.

**Response and template.** Boolean table: `Complete the capability row for {primitive_type}.`

**Derivation.** Apply the topic’s abstract primitive contracts, with caveats stated in the prompt.

**Difficulty.** L1 encoding/hash; L2 encryption/MAC; L3 signature/AEAD comparison.

**Examples.**

1. Cryptographic hash: unkeyed, not generally reversible, fixed digest length. L1.
2. Symmetric encryption: keyed, decryptable with key, not inherently fixed-length output. L2.
3. Signature: private-key operation, public verification, no confidentiality. L3.

**Distractors and validation.** Hash=encrypted or signature=secret. Versioned capability matrix.

### Cross-family progression

Operation classification and byte conversion precede all cipher work. Material roles should be revisited after each later category so “nonce,” “salt,” and “tag” acquire operational meaning rather than remaining vocabulary.

## 3. Category: Caesar shifts and tiny keyspaces

### Category purpose

Train forward, inverse, and key-recovery reasoning on the smallest complete substitution system while making its insecurity visible.

### Learn

With `A=0,...,Z=25`, add key `k` to encrypt and subtract it to decrypt, always modulo 26. There are only 26 shifts, so Caesar offers no meaningful modern security.

### Prerequisites

Alphabet-index mapping and canonical modular residues.

### Category boundaries

All messages are generated by the app. Brute-force families enumerate only the 26 Caesar keys and do not accept external ciphertext.

### Common misconceptions

- Using `A=1`.
- Shifting in the wrong direction.
- Failing to wrap after Z.
- Advancing/altering punctuation.
- Assuming a readable-looking candidate proves strong security.

### Family `caesar_encrypt`

**Task.** Encrypt letters or a short phrase with a supplied shift.

**Response and template.** Text: `Encrypt {plaintext} with Caesar shift {k}.`

**Derivation.** Map letters to 0..25, add k modulo 26, preserve nonletters.

**Difficulty.** L1 one/no wrap; L2 word with wrap; L3 phrase/punctuation.

**Examples.**

1. `ABC`, k=3 → `DEF`. L1.
2. `XYZ`, k=4 → `BCD`. L2.
3. `MEET AT 9!`, k=7 → `TLLA HA 9!`. L3.

**Distractors and validation.** Subtract key, no wrap, shift punctuation. Independent per-symbol oracle/round trip.

### Family `caesar_decrypt`

**Task.** Decrypt Caesar ciphertext with a supplied shift.

**Response and template.** Text: `Decrypt {ciphertext} encrypted with shift {k}.`

**Derivation.** Subtract k modulo 26.

**Difficulty.** L1 no wrap; L2 wrap; L3 negative/equivalent displayed key.

**Examples.**

1. `KHOOR`, k=3 → `HELLO`. L1.
2. `BCD`, k=4 → `XYZ`. L2.
3. `TLLA HA 9!`, k=33 → `MEET AT 9!` because 33≡7. L3.

**Distractors and validation.** Encrypt again or use 26−k incorrectly. Round trip.

### Family `caesar_recover_key`

**Task.** Recover the canonical shift from one or more aligned plaintext/ciphertext pairs.

**Response and template.** Integer `0..25`: `Under Caesar, {plain} encrypts to {cipher}. Find k.`

**Derivation.** For any letter pair compute `k=(c−p) mod26`; all pairs must agree.

**Difficulty.** L1 one pair; L2 wrap; L3 consistency across phrase or identify no single key.

**Examples.**

1. `A→F` → k=5. L1.
2. `Y→C` → k=4. L2.
3. `CAT→FDW` → k=3; `CAT→FAX` has no Caesar key. L3.

**Distractors and validation.** Absolute difference or A=1. Re-encrypt every supplied pair.

### Family `caesar_missing_symbol`

**Task.** Fill a missing plaintext, ciphertext, or mapping-table entry.

**Response and template.** Letter: `{caesar_equation_with_gap}; fill the missing symbol.`

**Derivation.** Apply forward or inverse shift to the aligned position.

**Difficulty.** L1 ciphertext gap; L2 plaintext gap; L3 infer k first.

**Examples.**

1. k=2, `A?C→CDE` → missing plaintext B. L1.
2. k=5, `MJQQT→H?LLO` → missing plaintext E. L2.
3. `A→D`, then `Z→?` under same key → C. L3.

**Distractors and validation.** Copy neighbor or fail wrap. Full mapping oracle.

### Family `caesar_compose_shifts`

**Task.** Combine or undo successive Caesar shifts.

**Response and template.** Canonical key/text: `A shift by {k1} followed by {k2} equals which single shift?`

**Derivation.** Add keys modulo 26; inverse shift is `−k`.

**Difficulty.** L1 small sum; L2 wrap; L3 include decrypt/unknown component.

**Examples.**

1. shifts 3 then 4 →7. L1.
2. shifts 20 then 11 →5. L2.
3. shift 9 then unknown gives net2 → unknown19. L3.

**Distractors and validation.** Multiply keys or omit modulo. Exhaust all 26 symbols.

### Family `caesar_candidate_enumeration`

**Task.** Generate/select plaintext candidates for every Caesar shift under a bounded fixture.

**Response and template.** Selected key/candidate: `Which row in the complete Caesar table for {ciphertext} matches {constraint}?`

**Derivation.** Decrypt under all 26 keys; choose using a supplied exact dictionary/template constraint.

**Difficulty.** L1 candidate supplied; L2 generate a subset; L3 two plausible words disambiguated by constraint.

**Examples.**

1. `KHOOR`; row k=3 is `HELLO`. L1.
2. `FDW` with constraint “a listed animal” → k=3, `CAT`. L2.
3. `UIF DBU` with the constraint “article followed by listed animal” → k=1, `THE CAT`; the whole constraint, not the first readable fragment, selects it. L3.

**Distractors and validation.** Choose first readable fragment. Fixture dictionary guarantees exactly one constraint match.

### Family `caesar_security_assess`

**Task.** Identify what Caesar hides and why its keyspace fails.

**Response and template.** Structured claims: `An attacker knows the algorithm and sees {ciphertext}. Which statements follow?`

**Derivation.** Count 26 keys; note preserved repeated-letter, spacing, and frequency structure.

**Difficulty.** L1 keyspace; L2 preserved patterns; L3 known-plaintext/key recovery.

**Examples.**

1. Maximum distinct Caesar keys →26 including identity. L1.
2. Plaintext repeated letters remain repeated at the same positions. L2.
3. One aligned letter pair determines the shift, so the remaining message decrypts. L3.

**Distractors and validation.** “Algorithm secrecy protects it” or `26!` keys. Rule/counterexample fixtures.

### Cross-family progression

Forward mapping precedes inverse mapping; then recover keys and compose shifts. Enumeration is introduced only after the learner can explain why all 26 candidates are complete. Security assessment is interleaved so fluent toy encryption is never mistaken for useful protection.

## 4. Category: Affine and monoalphabetic substitution

### Category purpose

Generalize shifts to keyed permutations, train mapping inversion and constraint reasoning, and expose the structural leakage of deterministic monoalphabetic substitution.

### Learn

Affine encryption maps `x` to `ax+b mod26`; `a` must be coprime to 26. A general monoalphabetic key is any permutation of the alphabet. In both, the same plaintext letter always maps to the same ciphertext letter, preserving equality patterns and much language structure.

### Prerequisites

Caesar, modular multiplication, GCD, and modular inverse for affine decryption.

### Category boundaries

The app uses generated keys and fixture messages. It teaches bounded pencil-and-paper analysis, not attacks on externally supplied ciphertext.

### Common misconceptions

- Treating every nonzero affine multiplier as invertible.
- Applying `a⁻¹y−b` instead of `a⁻¹(y−b)`.
- Forgetting that a substitution key must be one-to-one.
- Using encryption mapping in the wrong direction for decryption.
- Treating frequency evidence as certainty.

### Family `affine_key_validity`

**Task.** Decide whether `(a,b)` defines a permutation of 26 letters.

**Response and template.** Yes/no plus reason: `Is E(x)=({a}x+{b}) mod26 a valid affine cipher key?`

**Derivation.** Valid iff `gcd(a,26)=1`; b may be any residue.

**Difficulty.** L1 obvious unit/nonunit; L2 negative/equivalent a; L3 select all valid pairs.

**Examples.**

1. a=5,b=8 → valid, gcd(5,26)=1. L1.
2. a=2,b=7 → invalid; collisions occur. L2.
3. a=−5≡21,b=30≡4 → valid. L3.

**Distractors and validation.** a merely nonzero/prime or b must be coprime. GCD plus full permutation check.

### Family `affine_encrypt`

**Task.** Encrypt a symbol/string under a valid affine key.

**Response and template.** Text: `Encrypt {plaintext} with E(x)=({a}x+{b}) mod26.`

**Derivation.** Apply mapping independently to every letter.

**Difficulty.** L1 one letter; L2 wrapping word; L3 phrase/mixed scaffold.

**Examples.**

1. a=5,b=8, `A` → `I`. L1.
2. a=5,b=8, `B` (1) → `N` (13). L2.
3. a=7,b=3, `CAT` → `RDG`. L3.

**Distractors and validation.** Add before multiply or A=1. Mapping table/round trip.

### Family `affine_decrypt`

**Task.** Decrypt with the supplied key or inverse.

**Response and template.** Text: `Decrypt {ciphertext} under E(x)=({a}x+{b}) mod26.`

**Derivation.** Compute/receive `a⁻¹`, then `x=a⁻¹(y−b) mod26`.

**Difficulty.** L1 inverse supplied; L2 find inverse; L3 negative intermediate/string.

**Examples.**

1. a=5,b=8, inverse21, `I` → `A`. L1.
2. a=5,b=8, `N` → `B`. L2.
3. a=7,b=3, `RDG` → `CAT`. L3.

**Distractors and validation.** `a⁻¹y−b` or encrypt again. Independent inverse table/round trip.

### Family `affine_recover_key`

**Task.** Recover `(a,b)` from two usable aligned symbol pairs or decide uniqueness.

**Response and template.** Two integers/choice: `Given {p1}→{c1} and {p2}→{c2}, find the affine key if uniquely determined.`

**Derivation.** Subtract equations; solve `a(p1−p2)≡c1−c2 mod26`, then find b; enumerate valid a when division is nonunique.

**Difficulty.** L1 one pair includes A so b visible; L2 invertible difference; L3 none/multiple keys.

**Examples.**

1. `A→I`, `B→N` → b=8,a=5. L1.
2. `C→R`, `D→Y` → difference gives a=7, then b=3. L2.
3. `A→I` and `N→V` force b=8 but are satisfied by every valid affine multiplier because `13a≡13 mod26` for every unit a; return 12 candidate keys, not a unique a. L3.

**Distractors and validation.** Ordinary division or ignore affine-key validity. Enumerate all 12 valid multipliers and 26 offsets.

### Family `substitution_encrypt`

**Task.** Encrypt with a displayed arbitrary substitution alphabet.

**Response and template.** Text: `Using {plain_alphabet}→{cipher_alphabet}, encrypt {plaintext}.`

**Derivation.** Look up each plaintext letter by position in the mapping.

**Difficulty.** L1 short/table highlighted; L2 word; L3 phrase with repetitions.

**Examples.**

1. mapping begins `A→Q,B→W,C→E`; `CAB` → `EQW`. L1.
2. Under Atbash (`A→Z,...,Z→A`), `MEET` → `NVVG`; both E values map to V. L2.
3. Under the same mapping, `MEET AT 9!` → `NVVG ZG 9!`, preserving spaces, punctuation, and repetition. L3.

**Distractors and validation.** Use inverse row or advance mapping by position. Generated permutation oracle.

### Family `substitution_decrypt`

**Task.** Invert a displayed substitution mapping and decrypt.

**Response and template.** Text: `Using the mapping {mapping}, decrypt {ciphertext}.`

**Derivation.** Build inverse permutation once; map ciphertext symbols through it.

**Difficulty.** L1 inverse row shown; L2 derive inverse; L3 partial mapping with uniquely constrained gaps.

**Examples.**

1. `A→Q,B→W,C→E`; `EQW` → `CAB`. L1.
2. Under Atbash, ciphertext `NVVG` → `MEET`. L2.
3. A displayed permutation omits only mappings `Y→B` and `Z→A`; completing its unused ciphertext letters lets `BA` decrypt to `YZ`. L3.

**Distractors and validation.** Apply forward row. Inverse composition must be identity on all 26 letters.

### Family `substitution_mapping_consistency`

**Task.** Decide whether observed letter pairs can belong to one monoalphabetic substitution key.

**Response and template.** Yes/no/witness: `Can {aligned_pairs} come from one monoalphabetic substitution?`

**Derivation.** A plaintext symbol has one image and two plaintext symbols cannot share an image.

**Difficulty.** L1 repeated plaintext conflict; L2 ciphertext collision; L3 whole-word equality pattern.

**Examples.**

1. `A→Q` and `A→R` → impossible. L1.
2. `A→Q` and `B→Q` → impossible for a permutation. L2.
3. `MEET` has pattern `0-1-1-2`; candidate `ABBA` has `0-1-1-0`, so it cannot be its substitution. L3.

**Distractors and validation.** Check only one direction of one-to-one mapping. Bijection constraint oracle.

### Family `substitution_pattern_inference`

**Task.** Filter candidate words using repeated-letter patterns and supplied partial mappings.

**Response and template.** Selected candidate/mapping: `Cipher word {cipherword} has {constraints}; which candidate plaintexts remain possible?`

**Derivation.** Canonicalize equality pattern and enforce all known one-to-one pairs.

**Difficulty.** L1 repeated pair; L2 pattern plus length; L3 several words share a mapping.

**Examples.**

1. `ABBA` can match `NOON`, not `MOON`. L1.
2. pattern `0-1-2-0` matches `ELSE`, not `EAST`. L2.
3. Cipher words `ABBA ACD`: candidate pair `NOON NET` is jointly consistent, while `NOON NOD` would map distinct cipher symbols B and C to the same plaintext O. L3.

**Distractors and validation.** Letter frequency alone or local mappings that conflict globally. Exhaust fixture candidates.

### Family `substitution_frequency_evidence`

**Task.** Interpret controlled frequency evidence without treating it as proof.

**Response and template.** Ranked choice: `Given {cipher_counts} and {language_model}, which mapping is the best-supported hypothesis?`

**Derivation.** Score candidate mappings against supplied expected frequencies/digrams; label conclusion probabilistic.

**Difficulty.** L1 dominant letter in long fixture; L2 two frequencies; L3 counts plus word pattern.

**Examples.**

1. Counts `{Q:40,X:12,M:9,...}` and a supplied model with E most frequent make `Q→E` the best-supported hypothesis, not a certainty. L1.
2. Q and X each occur 20 times, so unigram evidence ties; cipher digram `QZ` occurs 11 times and the supplied model ranks candidate plaintext `TH` above candidate `QX`, so hypothesis `QZ→TH` scores higher. L2.
3. Frequency favors `Q→E`, but a supplied known pair proves plaintext A maps to Q; reject the frequency proposal because exact evidence dominates. L3.

**Distractors and validation.** “Most common always equals E.” Versioned corpus score and exact constraint filter; avoid tiny/noisy fixtures without a unique best answer.

### Cross-family progression

Affine validity precedes encryption and decryption. General substitution begins with explicit tables, then moves to inverse mapping and bijection constraints. Pattern and frequency analysis remain controlled-evidence exercises and must not appear until exact mapping behavior is mastered.

## 5. Category: Polyalphabetic substitution and Vigenère

### Category purpose

Train per-position key alignment and show how a repeating key changes substitution mappings while still leaking periodic structure.

### Learn

Vigenère applies a Caesar shift selected by a repeating key: `C_i=P_i+K_i mod26`. The same plaintext letter may encrypt differently at different key positions. A repeating key is much weaker than a random one-use pad because its period repeats.

### Prerequisites

Caesar encryption/decryption and aligned table reasoning.

### Category boundaries

Vigenère is presented as an insecure historical cipher. Period discovery uses short generated fixtures with declared analysis tools; arbitrary ciphertext cracking is excluded.

### Common misconceptions

- Advancing the key over spaces.
- Using A as shift 1.
- Subtracting during encryption.
- Believing a long word used as a repeating key is an OTP.
- Treating every repeated ciphertext fragment as proof of the period.

### Family `vigenere_keystream_align`

**Task.** Expand and align a repeating letter key under a plaintext/ciphertext.

**Response and template.** Aligned text: `Repeat key {key} under {message} using the letters-only convention.`

**Derivation.** Advance key index only for alphabetic characters; preserve nonletter slots as blank markers.

**Difficulty.** L1 letters only; L2 spaces; L3 punctuation/multiline continuation.

**Examples.**

1. key `KEY`, message `HELLO` → aligned `KEYKE`. L1.
2. key `AB`, message `GO NOW` → letter alignment `AB AB A`. L2.
3. key `DOG`, message `MEET, 9 PM!` → the six message letters `MEETPM` align with `DOGDOG`; comma, spaces, digit, and exclamation mark consume no key letters. L3.

**Distractors and validation.** Restart key per word or advance on spaces. Deterministic alignment state machine.

### Family `vigenere_encrypt`

**Task.** Encrypt a short message with a supplied repeating key.

**Response and template.** Text: `Encrypt {plaintext} with Vigenère key {key}.`

**Derivation.** Align key; add corresponding 0-based indices modulo 26.

**Difficulty.** L1 key length1/short; L2 several key positions; L3 punctuation and wrap.

**Examples.**

1. `ABC` with key `B` → `BCD`. L1.
2. `ATTACKATDAWN` with key `LEMON` → `LXFOPVEFRNHR`. L2.
3. `MEET AT 9!` with key `KEY` → `WICD ER 9!`. L3.

**Distractors and validation.** A=1, decrypt direction, or key advances on punctuation. Independent per-letter oracle/round trip.

### Family `vigenere_decrypt`

**Task.** Decrypt a Vigenère message with its key.

**Response and template.** Text: `Decrypt {ciphertext} with Vigenère key {key}.`

**Derivation.** Align key and subtract indices modulo 26.

**Difficulty.** L1 one shift; L2 classic word; L3 punctuation/alignment.

**Examples.**

1. `BCD` with key `B` → `ABC`. L1.
2. `LXFOPVEFRNHR` with key `LEMON` → `ATTACKATDAWN`. L2.
3. `WICD ER 9!` with key `KEY` → `MEET AT 9!`. L3.

**Distractors and validation.** Add key or reset it at spaces. Round trip and alignment trace.

### Family `vigenere_recover_key_segment`

**Task.** Recover aligned key letters from known plaintext/ciphertext.

**Response and template.** Letter sequence: `Given {plaintext}→{ciphertext}, find the aligned key segment.`

**Derivation.** Compute `K_i=C_i−P_i mod26` at every letter position.

**Difficulty.** L1 one letter; L2 segment; L3 infer shortest compatible repeating key.

**Examples.**

1. `A→L` → key letter L. L1.
2. `ATTACK→LXFOPV` → `LEMONL`. L2.
3. recovered stream `ABCABCABC` has shortest displayed period `ABC`, not `ABCABC`. L3.

**Distractors and validation.** Plain minus cipher or nonminimal period. Re-encrypt and test every divisor period.

### Family `vigenere_period_trace`

**Task.** Group positions by a supplied/candidate key period and assess consistency.

**Response and template.** Grouping/yes-no: `If the key period is {r}, which positions share a Caesar shift?`

**Derivation.** Letter position i uses key index `i mod r`; punctuation positions are excluded.

**Difficulty.** L1 show indices; L2 phrase; L3 compare candidate periods against aligned evidence.

**Examples.**

1. period3 → letter positions 0,3,6 share a shift. L1.
2. In `GO NOW` with period2, letter positions `{G,N,W}` use key index0 and `{O,O}` use key index1. L2.
3. A known-plaintext shift stream `2,5,2,5,2,5` is consistent with period2 and also period4, but shortest period is2. L3.

**Distractors and validation.** Group raw character indices or claim observed period is unique without minimality. State-machine grouping/exhaustive divisor test.

### Family `vigenere_security_compare`

**Task.** Compare Caesar, repeating-key Vigenère, and a true one-time pad under stated key conditions.

**Response and template.** Ranked/structured choice: `Which construction has {property}, given {key_generation_and_use}?`

**Derivation.** Evaluate key repetition, entropy, length, secrecy, and reuse separately.

**Difficulty.** L1 identify repetition; L2 key length/effective period; L3 distinguish random long reused key from OTP.

**Examples.**

1. Vigenère key `DOGDOG...` repeats every3 letters and leaks periodic structure. L1.
2. A 100-character dictionary phrase repeated as key is not an OTP because it is not uniform random. L2.
3. A uniform message-length key reused for a second message ceases to satisfy one-time use. L3.

**Distractors and validation.** “Long key means OTP” or “letters instead of bits makes secure.” Requirement-bitset oracle.

### Cross-family progression

Alignment is a hard prerequisite for encryption/decryption. Recovering the aligned key stream follows direct work; shortest-period reasoning follows recovery. Security comparison prepares XOR and OTP while preventing the superficial equation “Vigenère with a long key = OTP.”

## 6. Category: XOR and byte-stream mechanics

### Category purpose

Make XOR a fluent reversible byte operation and connect bit changes, text encodings, and keystream encryption.

### Learn

XOR outputs 1 where bits differ. Applying the same mask twice restores the original. For equal-length byte strings, XOR acts independently at each position; it never carries between bits or bytes.

### Prerequisites

Fixed-width binary/hex bytes and ASCII mapping.

### Category boundaries

This category teaches the operation and reversible keystream equation. Whether a key stream is secure or reused belongs to OTP/modern-stream categories.

### Common misconceptions

- Computing OR instead of XOR.
- Carrying as in addition.
- Dropping leading zeroes.
- Reversing byte order.
- Repeating/truncating unequal operands without an explicit rule.

### Family `xor_bit_truth`

**Task.** Complete/apply the XOR truth table.

**Response and template.** Bit: `{left}⊕{right}=?`

**Derivation.** Return 1 iff bits differ.

**Difficulty.** L1 one bit; L2 choose contrast with OR; L3 infer missing bit.

**Examples.**

1. `0⊕1=1`. L1.
2. `1⊕1=0`, unlike OR. L2.
3. `?⊕1=0` →1. L3.

**Distractors and validation.** OR/AND/copy operand. Four-row truth table.

### Family `xor_byte_compute`

**Task.** XOR two bytes in binary or hex.

**Response and template.** Fixed-width byte: `Compute {left}⊕{right} in {format}.`

**Derivation.** Align eight bits and XOR independently; format to requested width.

**Difficulty.** L1 sparse bits; L2 arbitrary hex; L3 mixed input/output representation.

**Examples.**

1. `00001111⊕00110011=00111100`. L1.
2. `A5⊕3C=99`. L2.
3. hex `D2` XOR binary `01101100` → binary `10111110` (`BE`). L3.

**Distractors and validation.** OR, AND, binary addition. Integer XOR plus bit-by-bit oracle.

### Family `xor_byte_string`

**Task.** XOR equally long byte strings position by position.

**Response and template.** Byte string: `{left_bytes}⊕{right_bytes}=?`

**Derivation.** Check equal lengths; pairwise XOR without endian reinterpretation.

**Difficulty.** L1 two bytes; L2 four; L3 sparse mask and unchanged positions.

**Examples.**

1. `00 FF ⊕ FF 00 = FF FF`. L1.
2. `41 42 43 ⊕ 01 02 03 = 40 40 40`. L2.
3. `DE AD BE EF ⊕ 00 FF 00 FF = DE 52 BE 10`. L3.

**Distractors and validation.** Reverse one string or combine as large integer incorrectly. Pairwise and packed-BigInt oracles agree.

### Family `xor_missing_operand`

**Task.** Recover plaintext, key, or ciphertext from the other two.

**Response and template.** Byte/string: `{known1}⊕?={known2}.`

**Derivation.** XOR the two known values because XOR is self-inverse.

**Difficulty.** L1 one byte; L2 string; L3 representations differ.

**Examples.**

1. `3A⊕?=7F` →45. L1.
2. `P=41 42`, `C=10 20` → key `51 62`. L2.
3. ciphertext `99`, key binary `00111100` → plaintext `A5`. L3.

**Distractors and validation.** Subtract bytes or complement. Substitute into original equation.

### Family `xor_text_transform`

**Task.** Encode ASCII, XOR bytes, and render the requested result.

**Response and template.** Byte/text fields: `XOR ASCII {text} with {key_bytes}; give {target}.`

**Derivation.** Encode to ASCII, verify length, pairwise XOR, then render hex or printable text.

**Difficulty.** L1 one printable result; L2 hex result; L3 recover text from hex/key.

**Examples.**

1. ASCII `A` (`41`) XOR `01` → `40` (`@`). L1.
2. `CAT` (`43 41 54`) XOR `01 02 03` → `42 43 57`. L2.
3. `10 20` XOR key `51 62` → `41 42` → `AB`. L3.

**Distractors and validation.** XOR alphabet indices or decimal character digits. Encode/byte/round-trip pipeline.

### Family `xor_repeating_key`

**Task.** Expand a short key over data and XOR it.

**Response and template.** Byte string: `Repeat key {key_bytes} over {data_bytes} and XOR.`

**Derivation.** At data position i use `key[i mod keyLength]`.

**Difficulty.** L1 exact multiple; L2 partial repetition; L3 missing key byte from several positions.

**Examples.**

1. data `01 02 03 04`, key `FF` → `FE FD FC FB`. L1.
2. data `10 20 30 40 50`, key `01 02` → `11 22 31 42 51`. L2.
3. ciphertext/plaintext reveal keystream `AA BB AA BB`; shortest repeating key is `AA BB`. L3.

**Distractors and validation.** Concatenate once then stop or reset at blocks. Modular-index oracle and round trip.

### Family `xor_bit_flip_trace`

**Task.** Predict exactly which bits/bytes change when an XOR mask is applied.

**Response and template.** Mask/result/positions: `Apply mask {delta} to {value}; which positions toggle?`

**Derivation.** Bits under mask 1 toggle; mask 0 preserves.

**Difficulty.** L1 one bit; L2 byte mask; L3 compare effect before/after XOR decryption.

**Examples.**

1. `1010⊕0010=1000`; the third bit from the left toggles. L1.
2. `55⊕0F=5A`; low nibble toggles. L2.
3. If `C=P⊕K`, replacing C by `C⊕80` flips the top bit of recovered P. L3.

**Distractors and validation.** Set bits to mask values rather than toggle. XOR difference must equal mask.

### Cross-family progression

One-bit truth precedes byte computation; direct XOR precedes missing operands. Text conversion is introduced only after byte accuracy. Repeating keys and bit-flip traces prepare the security consequences in the next category.

## 7. Category: One-time pads and keystream reuse

### Category purpose

Train exact OTP encryption mechanics and, more importantly, the requirements and failure consequences that distinguish a true OTP from “XOR with something.”

### Learn

OTP encryption is `C=P⊕K`, but the equation alone is not enough. K must be uniform random, independent, secret, message-length, and used once. Reuse cancels K between ciphertexts. OTP gives confidentiality under its assumptions but no integrity.

### Prerequisites

XOR strings, missing operands, and basic probability language.

### Category boundaries

All pads/messages are app-generated. Reuse-analysis questions expose only tiny fixture plaintexts and never accept external ciphertext.

### Common misconceptions

- Calling any XOR cipher an OTP.
- Assuming a random pad may be reused safely.
- Claiming `C₁⊕C₂` equals one plaintext.
- Believing perfect secrecy includes integrity.
- Believing an OTP solves key distribution/storage automatically.

### Family `otp_encrypt_decrypt`

**Task.** Encrypt/decrypt a short byte message with a same-length pad.

**Response and template.** Byte string: `{operation} {input_bytes} with pad {pad_bytes}.`

**Derivation.** Pairwise XOR; identical operation decrypts.

**Difficulty.** L1 one byte; L2 string; L3 text/hex boundary.

**Examples.**

1. P=`3C`, K=`A5` → C=`99`. L1.
2. C=`10 20`, K=`51 62` → P=`41 42`. L2.
3. ASCII `CAT`, K=`10 20 30` → C=`53 61 64`; decrypting restores `CAT`. L3.

**Distractors and validation.** Add/subtract or pad misalignment. XOR/round trip.

### Family `otp_requirement_audit`

**Task.** Decide whether a described key process qualifies as a one-time pad and identify failed requirements.

**Response and template.** Yes/no plus requirement set: `Does {key_process} produce a valid OTP for {message_use}?`

**Derivation.** Test uniformity, independence, secrecy, length, and single use independently.

**Difficulty.** L1 obvious short/repeating; L2 random but reused; L3 several records/storage details.

**Examples.**

1. Repeating password `DOG` over 1 KB → no: nonrandom and too short/repeated. L1.
2. 32 uniform independent random bytes for one 32-byte message, kept secret and destroyed after use → qualifies mechanically. L2.
3. Two independent-looking 64-byte messages use the same random 64-byte pad → no: reuse. L3.

**Distractors and validation.** “Unpredictable to me”=uniform or encryption algorithm fixes reuse. Requirement bitset.

### Family `otp_reuse_relation`

**Task.** Derive the XOR relation exposed by two ciphertexts that reused a pad.

**Response and template.** Byte string/expression: `Given C1={c1}, C2={c2} under the same pad, compute what the attacker obtains.`

**Derivation.** `C₁⊕C₂=(P₁⊕K)⊕(P₂⊕K)=P₁⊕P₂`.

**Difficulty.** L1 expression; L2 bytes; L3 identify what is and is not known.

**Examples.**

1. Symbolically, pad terms cancel and result is `P₁⊕P₂`. L1.
2. C₁=`AA 10`, C₂=`F0 30` → `5A 20`. L2.
3. From `P₁⊕P₂` alone neither plaintext is generally determined; selecting “both plaintexts immediately known” is wrong. L3.

**Distractors and validation.** Result K, P₁, or P₂. Algebraic normalization/pairwise XOR.

### Family `otp_reuse_known_plaintext`

**Task.** Use one known plaintext/ciphertext pair to recover the reused pad segment and another plaintext segment.

**Response and template.** Named byte fields: `C1={c1}, known P1={p1}, C2={c2}; recover {target}.`

**Derivation.** `K=P₁⊕C₁`; then `P₂=C₂⊕K` over aligned known length.

**Difficulty.** L1 one byte; L2 segment; L3 partial knowledge/offset.

**Examples.**

1. P₁=`41`, C₁=`10` → K=`51`; C₂=`13` → P₂=`42`. L1.
2. P₁=`41 42`, C₁=`10 20` → K=`51 62`; C₂=`12 21` → P₂=`43 43`. L2.
3. Known bytes cover offsets 2..4 only, so recover only those bytes of the other message—not the entire message. L3.

**Distractors and validation.** Apply known plaintext directly to C₂ or overclaim uncovered positions. Reconstruct both equations.

### Family `otp_malleability`

**Task.** Predict an unauthenticated ciphertext modification’s effect on plaintext.

**Response and template.** Byte string/claim: `If attacker changes C to C⊕{delta}, what decrypts?`

**Derivation.** Decrypted result is `P⊕delta`; key cancels.

**Difficulty.** L1 one toggled bit; L2 chosen byte delta; L3 choose delta from known old/new plaintext.

**Examples.**

1. Flip mask `01` on C → low plaintext bit flips. L1.
2. To change known byte `41` to `61`, use delta `20`. L2.
3. The recipient cannot detect this from OTP ciphertext alone; an authentication mechanism is required. L3.

**Distractors and validation.** Ciphertext modification randomizes all bytes or OTP detects it. XOR difference oracle.

### Family `otp_pad_accounting`

**Task.** Allocate nonoverlapping pad segments to messages and determine remaining usable bytes.

**Response and template.** Interval/integer: `Pad has {n} bytes; segments {uses} are consumed. Is {request} permitted and what remains?`

**Derivation.** Treat every used byte index as permanently consumed; require requested message length and no overlap.

**Difficulty.** L1 sequential use; L2 offsets; L3 aborted/transmitted messages still consume exposed pad segment.

**Examples.**

1. 100-byte pad, first 30 bytes used →70 unused sequential bytes. L1.
2. Used ranges `[0,31]` and `[64,79]`; a 16-byte request may use `[32,47]`, not overlap. L2.
3. Ciphertext was transmitted then delivery failed; its pad bytes remain consumed and cannot be retried with new plaintext. L3.

**Distractors and validation.** Reclaim failed-message bytes or count messages not bytes. Interval-set oracle.

### Family `otp_security_claim`

**Task.** Judge bounded claims about confidentiality, integrity, key distribution, and metadata.

**Response and template.** True/false with controlled reason: `Under {otp_assumptions}, does {claim} follow?`

**Derivation.** Apply OTP guarantee only to message content under ideal assumptions; assess integrity/metadata/key logistics separately.

**Difficulty.** L1 confidentiality; L2 integrity; L3 metadata/key-distribution qualification.

**Examples.**

1. Ideal OTP ciphertext alone reveals no information about equal-length plaintext content → true. L1.
2. Ideal OTP detects ciphertext modification → false. L2.
3. OTP does not hide message length and requires secure pad distribution/storage → true. L3.

**Distractors and validation.** “Perfect secrecy means perfect security.” Versioned guarantee matrix.

### Cross-family progression

Direct OTP transformation is brief because XOR is already mastered. Requirement audit begins immediately. Reuse relation precedes known-plaintext recovery; malleability follows bit-flip mechanics. Pad accounting and security claims connect mathematical properties to operational feasibility.

## 8. Category: Modern symmetric encryption and AEAD

### Category purpose

Train correct handling of nonce-based encryption records and recognition of the confidentiality/integrity consequences of common mode choices.

### Learn

Modern applications should normally use authenticated encryption. A record supplies a key, unique nonce, plaintext, and optional associated data; encryption returns ciphertext and tag. Decryption verifies the tag before releasing plaintext. Nonces may be public but must follow the scheme’s per-key uniqueness requirements.

### Prerequisites

XOR reuse/malleability, material roles, and security properties.

### Category boundaries

The learner never computes AES/ChaCha output by hand. Exact byte outputs use embedded published-style known-answer fixtures or an independently tested local primitive only; most questions operate on record metadata and guarantees.

### Common misconceptions

- Treating a nonce as a secret mini-key.
- Reusing a nonce after a process restart or counter reset.
- Believing encryption automatically detects modification.
- Assuming AAD is encrypted.
- Releasing plaintext before tag verification.
- Treating AEAD as replay protection without protocol state.

### Family `stream_nonce_counter_trace`

**Task.** Construct/check nonce-and-counter input labels for a hypothetical stream-cipher record.

**Response and template.** Ordered labels: `With nonce {nonce} and block counter starting at {start}, label {count} keystream blocks.`

**Derivation.** Hold record nonce fixed and increment the declared block counter without wrap.

**Difficulty.** L1 short sequence; L2 boundaries; L3 detect duplicate/wrap across records.

**Examples.**

1. nonce N7, counters 0..2 → `(N7,0),(N7,1),(N7,2)`. L1.
2. start254 in an 8-bit teaching counter for two blocks →254,255; a third would wrap and is rejected. L2.
3. Records `(N4,0..2)` and `(N4,0..1)` repeat keystream labels and are unsafe under the hypothetical construction. L3.

**Distractors and validation.** Increment nonce per block or allow counter wrap. Tuple uniqueness/range oracle.

### Family `nonce_uniqueness_audit`

**Task.** Inspect records/key epochs and find nonce reuse under the same key.

**Response and template.** Record set: `Which records violate the stated “nonce unique per key” rule?`

**Derivation.** Compare `(keyId,nonce)` pairs; repeated nonce under a different key is not a violation of this particular rule.

**Difficulty.** L1 one key; L2 key rotation; L3 restart/parallel senders.

**Examples.**

1. K1 uses nonces 0,1,1 → third record duplicates second. L1.
2. `(K1,7)` and `(K2,7)` do not collide per key; `(K2,7)` repeated does. L2.
3. Two senders share K9 and each start a local counter at0 → their first records reuse `(K9,0)`. L3.

**Distractors and validation.** Nonce globally unique forever or secret nonce makes duplication safe. Exact tuple grouping.

### Family `ecb_pattern_leakage`

**Task.** Predict equality patterns of ciphertext blocks under deterministic ECB-like block encryption.

**Response and template.** Block pattern: `Plaintext block pattern {pattern} is encrypted independently under one key; give ciphertext equality pattern.`

**Derivation.** Equal plaintext blocks map to equal ciphertext blocks; distinct blocks map to distinct blocks for a block-cipher permutation.

**Difficulty.** L1 repeated pair; L2 longer structure; L3 compare with randomized/nonce-based scheme.

**Examples.**

1. plaintext `A A` → ciphertext pattern `X X`. L1.
2. `A B A C B` → `W X W Y X` for distinct opaque blocks W,X,Y. L2.
3. The same plaintext block A appears in two records with distinct nonces; unlike ECB under one key, their ciphertext blocks have no required equality relation. L3.

**Distractors and validation.** Same key means all blocks same or encryption destroys equality relation. Canonical pattern oracle.

### Family `block_padding_length`

**Task.** Determine padding bytes and padded length under a fully specified PKCS#7-style rule.

**Response and template.** Integer/byte sequence: `Block size {b}; message length {n}. How many padding bytes, and what value?`

**Derivation.** `p=b−(n mod b)`, with `1≤p≤b`; append p bytes each numerically equal to p.

**Difficulty.** L1 nonboundary; L2 nearly full; L3 exact multiple requires full block.

**Examples.**

1. block8, length5 → three bytes `03 03 03`, padded length8. L1.
2. block16, length15 → one byte `01`. L2.
3. block16, length16 → sixteen `10` bytes, padded length32. L3.

**Distractors and validation.** Zero padding at exact multiple or use message remainder as byte. Formula plus parse/unpad round trip.

### Family `aead_record_fields`

**Task.** Place values into key, nonce, plaintext, AAD, ciphertext, and tag roles.

**Response and template.** Structured record: `Build the AEAD call/record from {scenario_fields}.`

**Derivation.** Secret content goes in plaintext, visible-but-bound metadata in AAD, unique public value in nonce; key is never serialized as a record field.

**Difficulty.** L1 identify inputs; L2 header/body; L3 route identifier that must remain visible yet authenticated.

**Examples.**

1. Secret message is plaintext; counter7 is nonce; shared secret K is key. L1.
2. Visible content type must not be alterable → AAD. L2.
3. Record stores `nonce || AAD header || ciphertext || tag`; it must not store the key. L3.

**Distractors and validation.** Encrypt nonce, place secret in AAD, transmit key. Typed field schema.

### Family `aead_aad_reasoning`

**Task.** Determine which fields are hidden and/or authenticated and what changes invalidate a tag.

**Response and template.** Property table: `For AEAD record {diagram}, mark each field hidden/authenticated.`

**Derivation.** Plaintext is encrypted and authenticated via ciphertext/tag; AAD is visible and authenticated; nonce is typically visible and is cryptographically bound according to the scheme model.

**Difficulty.** L1 AAD visibility; L2 tamper consequence; L3 omitted header field.

**Examples.**

1. Content type in AAD is readable by observer but protected from undetected change. L1.
2. Changing AAD while retaining old tag causes verification failure. L2.
3. A routing field left outside both ciphertext and AAD is neither hidden nor authenticated by this AEAD record. L3.

**Distractors and validation.** AAD=additional encrypted data or all serialized fields automatically bound. Field-coverage oracle.

### Family `aead_verify_then_release`

**Task.** Trace receiver behavior for valid/invalid tags and incomplete records.

**Response and template.** Ordered sequence/outcome: `Given {record_status}, what may the receiver release?`

**Derivation.** Parse within bounds, run authenticated decryption, release plaintext only on successful verification; otherwise return generic failure.

**Difficulty.** L1 valid/invalid; L2 streaming temptation; L3 application action ordered before verification.

**Examples.**

1. Valid tag → release verified plaintext. L1.
2. Invalid tag → reject and release no plaintext. L2.
3. Acting on an unverified command before final tag check is unsafe even if failure is reported later. L3.

**Distractors and validation.** Return “best effort” plaintext or reveal which byte failed. Protocol state machine.

### Family `encryption_authentication_compare`

**Task.** Choose between encryption-only, MAC-only, separate composition, and AEAD for stated properties.

**Response and template.** Construction/property choice: `Which provided construction satisfies {requirements} under {assumptions}?`

**Derivation.** Evaluate confidentiality and authenticity independently; for separate composition accept only a precisely defined safe construction in the prompt.

**Difficulty.** L1 one property; L2 both; L3 metadata plus replay requirement.

**Examples.**

1. Need secrecy and tamper detection → AEAD among encryption-only/MAC-only/AEAD. L1.
2. Internal log entry checked only by Alice and Bob, who share K, needs authenticity but no secrecy → MAC; a publicly verifiable variant would require a signature. L2.
3. AEAD protects record contents but does not by itself stop replay; add checked sequence/freshness state. L3.

**Distractors and validation.** Encryption=integrity or MAC=confidentiality. Guarantee bitsets plus construction assumptions.

### Cross-family progression

Nonce/counter labels precede multi-record audits. ECB and padding teach why “a block cipher exists” is not a safe design. AEAD field placement precedes tamper outcomes and verify-before-release. Replay remains deferred to protocol-state work.

## 9. Category: Hashes, MACs, and password protection

### Category purpose

Train selection and interpretation of one-way digests, keyed authentication, and deliberately expensive password verification.

### Learn

A hash is deterministic and fixed-length but unkeyed. A trusted expected digest can detect change; an attacker who may replace both file and digest defeats that check. A MAC uses a secret key. Password records use a unique salt and password KDF, not fast unsalted hashing.

### Prerequisites

Primitive roles, byte encodings, and integrity/authenticity distinction.

### Category boundaries

The app does not ask learners to calculate SHA/HMAC internals. Exact standard digests/tags, when shown, come from versioned fixed fixtures or a validated local provider and are representation exercises rather than memorization.

### Common misconceptions

- Hashes are reversible encryption.
- Matching an untrusted digest authenticates a download.
- Salts must be secret.
- One global salt is equivalent to per-record salts.
- A fast general-purpose hash is ideal for passwords.
- A MAC is publicly verifiable.

### Family `hash_determinism_length`

**Task.** Predict equality and output length from abstract hash calls.

**Response and template.** Equality/length: `Given idealized {hash_name} calls on {inputs}, which digests must be equal and how long are they?`

**Derivation.** Identical byte inputs under the same algorithm produce identical fixed-length outputs; different inputs are not guaranteed distinct.

**Difficulty.** L1 same input; L2 encoding difference; L3 collision caveat.

**Examples.**

1. H(`41`) called twice → same digest. L1.
2. ASCII `A` (`41`) and text characters `4`,`1` (`34 31`) are different inputs, so no equality is implied. L2.
3. Two distinct inputs may theoretically collide; “must differ” is too strong. L3.

**Distractors and validation.** Random hash output or equal-looking text means equal bytes. Input-byte identity/rule model.

### Family `digest_representation_length`

**Task.** Convert digest byte length to hex/Base64 character count under supplied padding rules.

**Response and template.** Integer: `A digest has {n} bytes. How many {encoding} characters encode it?`

**Derivation.** Hex uses 2 characters/byte. Base64 uses `4·ceil(n/3)` characters including padding.

**Difficulty.** L1 hex; L2 Base64 multiple of3; L3 Base64 padding boundary.

**Examples.**

1. 32-byte digest →64 hex characters. L1.
2. 24 bytes →32 Base64 characters. L2.
3. 20 bytes →28 Base64 characters including one `=` padding character. L3.

**Distractors and validation.** Bits confused with bytes or omit Base64 padding. Formula plus encoder length.

### Family `hash_property_identify`

**Task.** Identify preimage, second-preimage, or collision scenario from a controlled description.

**Response and template.** Single choice: `Which property/attack goal is described by {goal}?`

**Derivation.** Preimage: given digest find any input; second preimage: given input find distinct equal-hash input; collision: find any distinct pair.

**Difficulty.** L1 preimage; L2 collision; L3 contrast second preimage/collision.

**Examples.**

1. Given h, seek m with H(m)=h → preimage. L1.
2. Seek any m₁≠m₂ with equal hashes → collision. L2.
3. Given fixed contract m₁, seek different m₂ with same hash → second preimage. L3.

**Distractors and validation.** Swap collision and second preimage. Goal-schema oracle.

### Family `trusted_digest_scenario`

**Task.** Determine whether a digest check supplies useful integrity/authenticity under stated trust channels.

**Response and template.** Yes/no/property: `File and expected digest arrive via {channels}; what does comparison establish?`

**Derivation.** Check whether attacker can replace expected digest as well as file.

**Difficulty.** L1 trusted digest; L2 same untrusted channel; L3 signed digest/metadata.

**Examples.**

1. Expected digest obtained from a separately authenticated channel; match detects file change relative to it. L1.
2. File and digest on the same attacker-controlled page → attacker can replace both; no authenticity. L2.
3. A verified signature covers digest and filename → matching file hash binds content to signed metadata under stated key trust. L3.

**Distractors and validation.** Hash always proves origin. Attacker-capability set model.

### Family `mac_role_and_verification`

**Task.** Trace MAC creation/verification and determine who can forge/verify.

**Response and template.** Key/party/outcome fields: `Given parties {parties} and shared keys {keys}, who can create or verify {tag}?`

**Derivation.** Anyone holding the same MAC key can compute valid tags; outsiders cannot under the ideal primitive model.

**Difficulty.** L1 two parties; L2 several group keys; L3 distinguish group attribution/public verification.

**Examples.**

1. Alice and Bob share K; both can create and verify `MAC_K(M)`. L1.
2. Carol lacks K and cannot verify/forge in the model. L2.
3. Bob cannot prove to a third party that Alice authored a MAC because Bob could have produced it too. L3.

**Distractors and validation.** Verifier key is public or only sender can MAC. Party-key incidence oracle.

### Family `mac_coverage_tamper`

**Task.** Determine which message fields a MAC authenticates and whether a modification is detected.

**Response and template.** Field set/outcome: `Tag is MAC_K({covered_serialization}); attacker changes {field}. Does verification fail?`

**Derivation.** Recreate exact unambiguous serialization; only covered bytes affect the tag.

**Difficulty.** L1 body covered; L2 uncovered header; L3 ambiguous concatenation.

**Examples.**

1. tag covers `amount=10`; changing covered bytes to20 fails verification. L1.
2. recipient field is outside MAC input; changing it is not detected by this tag. L2.
3. Concatenating variable fields without lengths can make `(AB,C)` and `(A,BC)` identical bytes; length-prefixing removes ambiguity. L3.

**Distractors and validation.** Tag covers whole object automatically. Exact serialization/coverage oracle.

### Family `password_record_audit`

**Task.** Diagnose a generated password-storage record/design.

**Response and template.** Safe/unsafe plus issue set: `Audit {password_storage_design}.`

**Derivation.** Require supported password KDF, per-record salt, stored parameters, adequate configured cost, and no plaintext/reversible-password storage.

**Difficulty.** L1 plaintext/fast hash; L2 salt handling; L3 migration/parameters.

**Examples.**

1. Store plaintext passwords → unsafe. L1.
2. Store `SHA-256(password)` without salt → unsafe: fast and identical passwords share digest. L2.
3. Store `{algorithm,parameters,salt,derivedValue}` with unique random salt; verify by rerunning KDF and allow rehash after parameter upgrade. L3.

**Distractors and validation.** Encrypt passwords or hide salt. Versioned policy-rule bitset; do not grade exact production cost numbers unless supplied.

### Family `salt_and_kdf_reasoning`

**Task.** Trace salt effects and compare KDF work under supplied abstract cost parameters.

**Response and template.** Equality/work estimate: `For records {records}, which computations/results can be shared?`

**Derivation.** KDF input includes password and salt; unique salts separate otherwise equal passwords. Compute only abstract supplied cost multiplication.

**Difficulty.** L1 same password/different salt; L2 duplicated salt; L3 cost upgrade.

**Examples.**

1. Same password with salts S1 and S2 should produce unrelated stored values in the model. L1.
2. Reusing one salt across all accounts enables shared precomputation and reveals equal-password equality for that salt. L2.
3. If an abstract KDF cost doubles and all else is equal, each guess costs twice as much; existing records retain their stored parameter until rehashed. L3.

**Distractors and validation.** Salt adds secrecy or changes required password. Record-input/cost model.

### Cross-family progression

Hash determinism and representation precede security properties. Trusted-digest scenarios introduce channel assumptions. MAC key roles precede coverage/serialization. Password records are learned as a specialized verifier construction, not as generic hashing.

## 10. Category: Public-key workflows and protocol state

### Category purpose

Train role-correct use of public-key primitives and stateful reasoning about identity, key establishment, certificates, replay, and compromise.

### Learn

Public keys may be distributed; private keys remain controlled by their owner. Signatures authenticate covered bytes under a trusted public-key binding. Practical encryption is hybrid. Key agreement needs authentication to resist active impersonation. Valid cryptographic records can still be stale replays unless a protocol checks freshness.

### Prerequisites

Security properties, hashes/MACs, AEAD records, and attacker-capability reasoning.

### Category boundaries

No large-number arithmetic or curve-point computation is required. Tiny RSA/Diffie–Hellman arithmetic belongs in number theory if enabled; here the task is workflow and guarantees.

### Common misconceptions

- “Encrypt with the private key” is an adequate model of signatures.
- Signing hides a message.
- A public key’s mathematical validity establishes its owner.
- Unauthenticated key exchange prevents active interception.
- AEAD uniqueness automatically prevents replay.
- Certificate validity dates alone establish trust.

### Family `asymmetric_key_roles`

**Task.** Assign public/private key operations for encryption and signatures.

**Response and template.** Matching: `For {goal}, which party uses which key for which operation?`

**Derivation.** Confidentiality to Bob: encrypt/encapsulate to Bob’s public key, Bob decrypts with private. Alice signature: Alice private signs, Alice public verifies.

**Difficulty.** L1 one operation; L2 two parties; L3 encryption plus signature with distinct keys.

**Examples.**

1. Send secret to Bob → use Bob’s public encryption key; Bob uses his private key. L1.
2. Verify Alice’s signature → trusted Alice public verification key. L2.
3. Alice signs a message to Bob and encrypts it for Bob: Alice-private signing role and Bob-public encryption role are distinct. L3.

**Distractors and validation.** Own public key for recipient secrecy or recipient private key at sender. Role graph oracle.

### Family `signature_workflow`

**Task.** Order signing/verifying steps and determine verification outcome after modification.

**Response and template.** Ordered sequence/outcome: `Given {message}, {signature}, and trusted key binding, what does verifier do?`

**Derivation.** Recreate exact signed bytes/context, verify with public key, then act only if valid.

**Difficulty.** L1 unchanged/changed message; L2 metadata coverage; L3 verification before action.

**Examples.**

1. Signature made over M; verify same M with correct public key → valid in model. L1.
2. Change one signed field while keeping signature → invalid. L2.
3. Parsing executes an embedded command before signature verification → unsafe ordering even if verification later fails. L3.

**Distractors and validation.** Decrypt signature to reveal message or partial validity. Signed-byte/state-machine oracle.

### Family `signature_context_scope`

**Task.** Decide whether a valid signature can be transplanted to another context or leaves important fields unauthenticated.

**Response and template.** Yes/no/field set: `Signature covers {serialization}; is it valid authorization for {use}?`

**Derivation.** Check exact bytes, signer identity, purpose/domain label, recipient, and freshness fields required by scenario.

**Difficulty.** L1 omitted field; L2 same bytes/different purpose; L3 domain-separated formats.

**Examples.**

1. Amount is outside signed bytes → attacker may change amount without invalidating signature. L1.
2. A signature over raw `APPROVE` is ambiguous across two applications if no context is signed. L2.
3. Signing `domain || version || recipient || amount || nonce` binds all listed fields under an unambiguous encoding. L3.

**Distractors and validation.** Signature authenticates surrounding UI automatically. Coverage/context bitset.

### Family `hybrid_encryption_trace`

**Task.** Complete/order a hybrid-encryption sender/receiver workflow.

**Response and template.** Ordered sequence/matching: `Place {operations} into a valid hybrid-encryption flow.`

**Derivation.** Generate random session key; encapsulate/encrypt it to recipient public key; AEAD-encrypt data; recipient decapsulates with private key then verifies/decrypts AEAD.

**Difficulty.** L1 role match; L2 ordering; L3 multiple recipients/session keys.

**Examples.**

1. Large file is protected by symmetric AEAD, not directly transformed block-by-block with raw public-key operation. L1.
2. Sender creates session key K, protects K for Bob, and sends encapsulation plus AEAD record. L2.
3. A declared multi-recipient envelope for Bob and Carol: generate one K, encapsulate K separately to each trusted public key, AEAD-encrypt the file once, and authenticate the recipient list as metadata. L3.

**Distractors and validation.** Send session key plaintext or use public-key output as unauthenticated data stream. Typed workflow DAG.

### Family `key_exchange_authentication`

**Task.** Determine what authenticated or unauthenticated key exchange guarantees against passive/active attackers.

**Response and template.** Property/attack trace: `Given {exchange_diagram} and {attacker_capabilities}, what is established?`

**Derivation.** Passive secrecy may follow from ideal key agreement; active peer identity requires authenticated transcript/key binding.

**Difficulty.** L1 passive observer; L2 active relay; L3 signature/certificate binding.

**Examples.**

1. Ideal unauthenticated exchange can hide the resulting key from a passive observer. L1.
2. Active Mallory substitutes shares and establishes separate keys with Alice and Bob → peer identity not established. L2.
3. Each side verifies a signature over both ephemeral shares and identities under trusted keys → substitution trace fails in the model. L3.

**Distractors and validation.** Shared secret automatically identifies peer. Attacker transition simulator.

### Family `certificate_validation`

**Task.** Evaluate a simplified certificate path for name, issuer trust, validity time, usage, and revocation/status assumptions supplied.

**Response and template.** Accept/reject plus reason set: `At {time}, may certificate {leaf} authenticate {name} for {usage} under {trust_store}?`

**Derivation.** Verify every displayed signature/path link abstractly, trusted root, time interval, requested name, allowed usage, and supplied status.

**Difficulty.** L1 name/time; L2 chain/trust anchor; L3 several valid-looking paths or wrong usage.

**Examples.**

1. Certificate for `example.test` used for `other.test` → reject name mismatch. L1.
2. Dates valid but issuer root absent from supplied trust store → reject. L2.
3. Chain and name valid, but certificate allows signing code only, not server authentication → reject usage. L3.

**Distractors and validation.** Any signed certificate trusted or valid date sufficient. Explicit path constraint engine; no real certificate parsing.

### Family `replay_protection_trace`

**Task.** Process authenticated records through a sequence-number/nonce replay policy.

**Response and template.** Accept/reject plus updated state: `Receiver state is {state}; process record {record}.`

**Derivation.** First verify authenticity, then apply declared monotonic/window/challenge policy atomically and update state on acceptance.

**Difficulty.** L1 duplicate sequence; L2 out-of-order window; L3 key epoch/reset.

**Examples.**

1. Highest accepted sequence5, strict monotonic policy; authenticated sequence5 replay → reject. L1.
2. Window allows unseen 8..12; receive10 then9 → both accepted once, second copy of10 rejected. L2.
3. Sequence resets to0 only with a new authenticated key epoch; reset under same key/state is rejected. L3.

**Distractors and validation.** Valid tag means fresh or rejected packet advances state. Deterministic replay-window state machine.

### Family `compromise_and_forward_secrecy`

**Task.** Determine which generated records/keys are exposed after a specified compromise under a declared protocol model.

**Response and template.** Record/key set: `At time {t}, attacker obtains {material}; which sessions can be decrypted/forged?`

**Derivation.** Follow explicit key-derivation/lifetime edges; erased ephemeral secrets are unavailable; never infer guarantees absent from model.

**Difficulty.** L1 current symmetric key; L2 rotated epochs; L3 authenticated ephemeral exchange with/without erased secrets.

**Examples.**

1. Compromise of long-lived symmetric K exposes records encrypted under K if ciphertexts were recorded. L1.
2. Independent K2 after rotation does not become known merely from K1 under the declared no-derivation model. L2.
3. If past session keys came from erased ephemeral secrets and long-term signing key only authenticated exchanges, later signing-key compromise does not reveal past session keys in the model; it may enable future impersonation. L3.

**Distractors and validation.** One compromise exposes everything forever or key deletion erases captured ciphertext. Key-dependency graph reachability.

### Cross-family progression

Key-role matching precedes signature and hybrid workflows. Signature byte coverage precedes context/domain reasoning. Key exchange is paired with authentication, then certificates supply public-key identity binding. Replay and compromise families require the learner to track explicit protocol state rather than assume a primitive solves the whole system.

## 11. Topic-wide progression

Recommended order:

1. operation/property vocabulary and byte representations;
2. Caesar forward/inverse mapping and tiny keyspace;
3. affine validity, inversion, and general substitution tables;
4. substitution constraints and controlled frequency evidence;
5. Vigenère alignment and repeated-key structure;
6. XOR bits, bytes, strings, and missing operands;
7. OTP mechanics, requirements, reuse, and malleability;
8. nonces, records, ECB/padding consequences, and AEAD;
9. hashes, trusted digests, MAC coverage, salts, and password KDF records;
10. public/private key roles, signatures, hybrid encryption, and authenticated exchange;
11. certificates, replay state, key rotation, and compromise analysis.

Prerequisite gates:

- byte representation gates XOR and every exact byte-string family;
- Caesar direction gates affine and Vigenère;
- modular inverse gates affine decryption/key recovery;
- substitution bijection gates controlled pattern/frequency analysis;
- direct XOR and missing-operand mastery gate OTP reuse analysis;
- OTP reuse/malleability gates stream nonce and AEAD motivation;
- property/role classification gates construction selection;
- hash trust-channel reasoning gates MAC/signature distinctions;
- AEAD record reasoning gates hybrid encryption;
- signature key roles gate authenticated key exchange/certificates;
- record authentication gates replay-state reasoning.

Interleave deliberately:

- encoding versus encryption whenever representation changes;
- classical transformation fluency with explicit insecurity questions;
- encryption and decryption/missing-key directions;
- byte XOR and text/hex representations;
- valid OTP examples with almost-OTP counterexamples;
- nonce-unique and nonce-reused record sets;
- integrity without authenticity and authenticity without confidentiality;
- MAC/signature verification with coverage failures;
- cryptographically valid records with stale/replayed protocol states.

Do not mix more than three layers in one question. A Level 5 protocol diagnosis may combine identity binding, AEAD, and replay state, but should not also require manual text encoding or affine arithmetic.

Selection after sufficient history:

- 30% weakest family/misconception;
- 20% spaced mastered material;
- 15% inverse/missing-value transfer;
- 15% representation transfer;
- 10% attacker-knowledge or security-property diagnostics;
- 10% mixed record/protocol state.

## 13. Feedback and worked solutions

Worked solutions should:

1. restate the exact alphabet, byte, key-alignment, or protocol convention;
2. show the smallest relevant mapping/XOR/state table;
3. name the security property being evaluated;
4. list what each actor/attacker knows;
5. distinguish mathematical output from its security interpretation;
6. verify by round trip, inverse mapping, tag/state rule, or property model;
7. end historical/toy examples with the concise insecurity reminder when relevant.

Diagnostic examples:

> `1 XOR 1` is `0`, not `1`. Your byte matches OR. XOR sets a bit only when the input bits differ.

> The key repeats over letters, not characters. The space does not consume the next Vigenère key letter.

> This is XOR encryption, but not a one-time pad: the three-byte password repeats and is not a uniform independent message-length key.

> Reuse reveals `P₁⊕P₂`. That relation can become damaging with known or guessed plaintext, but it does not by itself equal either message.

> The nonce may be public. The problem is that `(K7, nonce 4)` already appeared under the same key.

> Associated data is authenticated but visible. Put the public content type in AAD when it must remain readable and tamper-evident.

> A matching digest helps only if the expected digest is trusted. Here the attacker can replace both the file and the value beside it.

> The tag is valid, but sequence 12 has already been accepted. Authenticity does not make a replay fresh.

Correct feedback should be concise and name the useful rule. Incorrect feedback should identify a recognizable alternative computation or omitted security assumption. It must not reveal secret fixture data that the learner’s current evidence would not justify.

## 14. Rendering, interaction, and accessibility

- Cipher mappings use semantic two-row tables with accessible `plaintext A maps to ciphertext Q` labels.
- Aligned plaintext/key/ciphertext rows preserve monospaced column alignment but also expose each column as an accessible table.
- Byte strings may wrap only between bytes, never inside a byte.
- Binary XOR views align bits vertically and include textual operands/result.
- Color is not the only cue for changed bits, reused nonces, covered fields, trusted links, or rejected records.
- Pattern-analysis letters use symbols/labels in addition to color.
- Protocol diagrams provide an ordered text transcript and name actors consistently.
- Security-property tables use explicit yes/no/conditional text, not icons alone.
- Failure states say `Rejected: authentication failed` without rendering unauthenticated plaintext as ordinary content.
- Historical-cipher and toy labels are visible to screen readers and never conveyed only by a warning color.
- Keyboard users can traverse mappings, byte cells, ordered steps, record timelines, and matching questions.
- Long fixed-width values support optional byte grouping and copy-free interaction; the app never asks the learner to paste secrets.

## 15. Generator and implementation requirements

### Classical cipher engine

Implement and independently test:

- alphabet normalization with locale-independent ASCII handling;
- canonical modulo for negative keys/intermediates;
- Caesar mapping/inverse/composition;
- affine key validation, modular inverse, mapping, and inverse;
- random permutation generation and inversion;
- equality-pattern canonicalization;
- Vigenère letter-only alignment and period detection;
- exact fixture-dictionary filtering under partial bijections.

Every generated full substitution alphabet must contain each permitted symbol exactly once. Frequency questions must be generated backward from a fixture and scoring rule that leaves one explicitly “best-supported” hypothesis; they must never word evidence as certainty.

### Byte/XOR engine

Represent bytes as `Uint8Array`-like values and implement:

- strict binary/hex parsing and fixed-width formatting;
- pairwise XOR with explicit length checks;
- repeating-key expansion only in its named insecure family;
- ASCII encode/decode for `0x20..0x7E` plus explicitly allowed controls;
- XOR difference and known-plaintext reconstruction;
- used-pad interval accounting;
- constant structural comparison for byte-string answers.

Do not use JavaScript’s signed 32-bit bitwise formatting directly without masking each result to `0xFF`.

### Modern primitive boundary

Core exercise availability must not depend on a backend, network, OS command, or secure-origin browser feature.

- Modern algorithms are modeled through versioned contracts, record metadata, and opaque fixture outputs.
- Exact SHA/MAC/AEAD byte-output questions are optional and may use embedded fixed known-answer fixtures.
- If an implementation bundles or invokes a vetted local cryptographic provider, it must pass embedded known-answer self-tests before those optional families are enabled.
- Do not create a simplified “AES-like” or “SHA-like” algorithm and then label its output AES/SHA.
- A deliberately tiny checksum/toy transform must be visibly named `toy` and must not be used to infer production security.
- The app must not generate, import, retain, or export production credentials or private keys.
- Question randomization is pedagogical randomness, not a production key-generation service.

### Controlled security-rule model

Scenario generation uses explicit typed facts:

`primitive`, `keyOwners`, `keyEpoch`, `nonce`, `nonceRule`, `coveredFields`, `hiddenFields`, `signedContext`, `trustBindings`, `attackerReads`, `attackerWrites`, `attackerCompromises`, `recordOrder`, `replayPolicy`, `erasedSecrets`, and `requiredProperties`.

Derive answers from rule evaluation:

- capability/role bitsets;
- exact byte coverage;
- `(keyEpoch,nonce)` uniqueness;
- protocol state transitions;
- graph reachability for key compromise;
- trust-path predicates;
- explicit ideal-primitive assumptions.

Do not let a language model or fuzzy text classifier determine correctness at runtime.

### Distractor construction

Every choice records the misconception transformation that produced it:

- wrong cipher direction;
- A=1 offset;
- omitted modulo/wrap;
- invalid affine inverse;
- forward rather than inverse mapping;
- Vigenère raw-character alignment;
- OR/AND/addition in place of XOR;
- key reuse cancellation overclaim;
- nonce/key/salt/tag role swap;
- encryption-only provides integrity;
- untrusted hash provides authenticity;
- MAC provides public proof;
- signature provides secrecy;
- valid tag provides freshness;
- trust path/name/usage check omitted.

Reject arbitrary nearby byte values or generic “all/none” distractors unless they reproduce a declared misconception.

### Offline and privacy constraints

All ordinary generation, checking, history, and explanations run in the standalone HTML/CSS/JS page. No content is uploaded. Free-form fields are bounded to generated-answer formats and must not invite real ciphertexts, passwords, tokens, or keys.

## 16. Automated validation

For every instance:

- every placeholder is substituted and every representation label is explicit;
- letter mappings use the declared alphabet convention;
- Caesar, affine, substitution, and Vigenère answers round-trip;
- affine a is invertible exactly when the instance claims;
- substitution maps are bijections and partial maps remain consistent;
- frequency/pattern fixtures have the promised unique best/valid answer;
- byte operands have declared equal length or explicit repeating rule;
- XOR is recomputed by independent byte and bit-string paths;
- missing XOR operands satisfy the original equation;
- OTP labels and requirement answers match all five normative requirements;
- reuse/known-plaintext answers reveal exactly the justified byte range;
- pad-allocation intervals never overlap and consumed ranges are not reused;
- nonce audits group by key epoch and flag every duplicate exactly once;
- block padding appends a nonempty valid block suffix and unpads uniquely;
- AEAD field/property answers match the declared record contract;
- invalid-tag workflows release no plaintext;
- hash/MAC/password answers use the versioned capability and policy model;
- serialization questions compare actual generated bytes, not display strings;
- signature coverage and context sets are exact;
- certificate fixtures satisfy or fail precisely the named path predicates;
- replay transitions are deterministic and do not update state on rejection;
- compromise answers equal reachability in the generated key-dependency graph;
- multiple-choice families have exactly one correct/best answer;
- every distractor is distinct and tagged with its misconception;
- no real-world or user-provided target data enters a generated cryptanalysis family.

Property/fuzz minimums:

- 100,000 Caesar/affine round trips across all valid keys and boundary letters;
- 50,000 random substitution permutations, inversions, and partial-map constraints;
- 100,000 Vigenère strings with punctuation/alignment variation;
- 250,000 byte/byte-string XOR and missing-operand cases;
- 50,000 OTP requirement/reuse/known-range/pad-allocation cases;
- 100,000 nonce/key-epoch record sets including restarts and rotations;
- exhaustive padding lengths for every supported block size and several blocks;
- 50,000 AEAD field/tamper/verification-state scenarios;
- 50,000 hash/MAC/password role and coverage scenarios;
- 50,000 signature/certificate/replay/compromise workflow scenarios;
- all embedded modern-primitive fixtures checked against their fixed expected bytes when optional exact-output support is enabled.

Deterministic seeded test runs must reproduce every generated prompt, answer, distractor provenance, and worked solution. A fixture/rule change increments its version and runs migration tests against saved history IDs.

## 17. Coverage requirements

Balance:

- encoding/encryption/hash/MAC/signature classifications;
- confidentiality, integrity, authenticity, and freshness singly and in combinations;
- encrypt/decrypt/recover-key directions;
- wrapping and nonwrapping alphabet arithmetic;
- valid and invalid affine multipliers;
- explicit/full/partial substitution mappings;
- exact pattern constraints and probabilistic frequency evidence;
- Vigenère key lengths, punctuation alignment, and shortest periods;
- binary, hex, byte-string, and ASCII XOR representations;
- zero/one/many toggled bits and leading-zero answers;
- true OTP and failures of randomness, length, secrecy, independence, or one-time use;
- reuse with no known text, partial known text, and bounded recovered ranges;
- nonce uniqueness across one key, rotations, senders, restarts, and counters;
- AEAD plaintext/AAD/nonce/tag field combinations and tampering;
- trusted and attacker-replaceable digest channels;
- MAC coverage, party key ownership, and serialization boundaries;
- password records with unique/reused/missing salts and versioned KDF parameters;
- public-key encryption/signature roles for different actors;
- valid/invalid certificate name, trust, time, usage, and status predicates;
- fresh, duplicate, out-of-order, and cross-epoch records;
- current/past/future compromise consequences under explicit models.

Within a session:

- suppress exact prompt repeats for at least 100 items;
- suppress the same structural signature for at least 20 items;
- avoid more than two consecutive raw cipher/byte calculations;
- after historical-cipher unlock, show at least one security-limit question per five transformation questions;
- after modern categories unlock, show at least one attacker/state question per four role/property questions;
- do not overrepresent Caesar because it is easy to generate.

## 18. Topic-level quality checklist

- [ ] Historical/toy ciphers are always labeled insecure.
- [ ] Cryptanalysis uses only bounded app-generated fixtures.
- [ ] No exercise solicits real secrets or external attack targets.
- [ ] Encoding, encryption, hash, MAC, and signature remain distinct.
- [ ] Alphabet, byte order, text encoding, and key alignment are explicit.
- [ ] Affine keys are validated as permutations.
- [ ] Substitution mappings are bijections and inverse direction is clear.
- [ ] Frequency evidence is never presented as certainty.
- [ ] XOR uses fixed-width bytes and exact length rules.
- [ ] OTP requires uniformity, independence, secrecy, message length, and one-time use.
- [ ] Reuse exercises do not overclaim what ciphertext XOR alone reveals.
- [ ] OTP/stream malleability motivates authentication.
- [ ] Nonce uniqueness is evaluated per key/epoch and across restarts/senders.
- [ ] AEAD authenticates before releasing plaintext.
- [ ] AAD visibility and coverage are stated correctly.
- [ ] AEAD is not presented as automatic replay protection.
- [ ] Hash integrity questions state how the expected digest is trusted.
- [ ] MAC and signature verifier/key roles are correct.
- [ ] Password exercises use salts and password KDFs, not fast bare hashes.
- [ ] Public-key workflows use hybrid encryption and trusted key binding.
- [ ] Certificate questions check name, path, time, usage, and supplied status.
- [ ] Protocol answers derive from explicit attacker and state models.
- [ ] Modern primitives are not reimplemented as misleading toy algorithms.
- [ ] Every family has at least three instantiated examples.
- [ ] Every family defines derivation, difficulty, misconceptions/distractors, and validation.
- [ ] Difficulty grows through reasoning and state, not message length.
- [ ] All core generation/checking works offline in the standalone page.
- [ ] Repeated practice improves both mechanical fluency and security judgment.
